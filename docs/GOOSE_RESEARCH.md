# goose (AAIF) research — lead-agent qualification inputs

**Research date:** 2026-09-16, web-verified. **Sources:** goose-docs.ai (docs stamped goose v1.50.1), github.com/aaif-goose/goose (releases; tracking issue #6642), agentclientprotocol.com (updates + agents index), AAIF announcements via goose-docs.ai/blog. **Companion plan:** `docs/superpowers/plans/2026-09-16-goose-qualification.md`.

Deep-research record for qualifying goose as a third `WORKFLOW_ACP_AGENT` kind and as a staged replacement candidate for the vendored-Cline SDK seam (`docs/ACP_DECISION.md` SDK seam retention). Follows the `ACP_RESEARCH → ACP_DECISION` convention: no claim below is probe evidence; every live claim lands only through the gated probes in the companion plan.

## 2. The ACP surface (what the hub would spawn)

- **Launch shapes:** `goose acp` (stdio subprocess — the hub's local/contained model, same shape as `opencode acp --pure`) and `goose serve` (HTTP/WS on 127.0.0.1:3284 at `/acp`, `X-Secret-Key` auth, `--dangerously-unauthenticated` exists; TLS + cert pinning supported). The HTTP/WS mode is the remote-agent axis: it sits outside the hub's whole-process bwrap containment, so it is out of scope for this qualification and noted as a THREAT_MODEL follow-up.
- **Protocol surface:** standard ACP v1 plus a large goose-specific extension surface, all namespaced `_goose/unstable/*` (config read/upsert/remove, config extension add/remove/set-enabled, session steer/export/import/archive/rename, `session/system-prompt/set`, recipes list/save/scan, schedules CRUD, `sources/*` (skills), `tools/call`, `tools/list`, `tools/permissions/set`, providers/catalog/custom/secrets, diagnostics, `session/working-dir/update`). All of these are client-to-agent methods: the hub as client simply declines to wire the dangerous ones; the driver must tolerate unknown methods and notifications (it already forwards unknown session update types unchanged).
- **Usage visibility:** goose emits a custom notification `_goose/unstable/session/update` whose union includes `usage_update` (plus `status_message`, `message_usage`) parallel to standard `session/update`. G7-family visibility is therefore expected Green; the probe confirms which channel(s) carry it.
- **Version stamping:** the ACP reference is generated from `crates/goose/acp-schema.json` at v1.50.1 — schema drift between weekly releases is a real qualification pinning concern (probe against one pinned version; re-run on bump, same as the OpenCode family's ambient-PATH caveat).

## 3. Enforcement surfaces (three layers, hub-relevant)

1. **ACP permission interception — `GOOSE_MODE=approve`.** goose's modes: `auto` (fully autonomous, the default), `approve` (asks before write tools; granular tool permissions supported), `smart_approve` (LLM-judged risk-based), `chat`. The hub would launch approve mode so mutations cross `session/request_permission` → `WorkflowApplication.authorize`, the same seam as Cline/OpenCode. **Honest risk:** goose's own docs say read/write classification in approval modes is a *best effort interpreted by the LLM provider* — an LLM-classified interception is fail-open by construction, weaker than OpenCode's config-owned permission surface. Consequences: the B3 probe (every mutating call must reach `request_permission`) is the pivotal enforcement probe, and the guard dispatcher + whole-agent bwrap remain the hard backstops regardless of goose's classification quality.
2. **Hooks — the Open Plugins hooks specification.** `PreToolUse` hooks can **deny** (exit 2 with stderr reason, or `{"decision":"block","reason":...}` on stdout; the model receives an explicit policy-denial message). `on_failure: block` makes a hook fail-closed (default is fail-open allow). `PreToolUseResult` is an observability event with `decision`/`cause` (`policy_denial` vs `hook_failure`), `policy_evaluated`, `blocked_by`, and a `tool_call_id` correlation key. `Stop` hooks can force a turn to continue (capped). Plugin discovery: user scope `~/.agents/plugins/<name>/` and **project scope `<project>/.agents/plugins/<name>/`** — the project scope is hub-composable inside the workspace without touching user state. Hooks run as local shell commands (inside the containment when goose is contained), payload JSON on stdin. **Known gap:** `SubagentStart`/`SubagentStop` lifecycle events are not emitted, and the docs do not state whether subagent-internal tool calls fire `PreToolUse`. Whether they do decides goose's candidacy as the Cline-seam replacement (host-hook visibility into subagent-internal calls is the one thing the seam retains; `docs/ACP_DECISION.md` "what it costs is Cline forever"). This is the single highest-value probe.
3. **Whole-process containment — unchanged.** Whole-agent Bubblewrap, the hub's posture for both prior agents. goose's own sandboxing (v1.25 "Sandboxed, Streamlined, and More Secure", container-use extension) nests harmlessly inside. Note: hooks plugins are discovered from home-dot paths (`~/.agents/plugins`) that resolve to the scratch HOME inside containment — the hub controls what exists there; probe confirms discovery paths under containment.

**fs delegation posture:** goose executes file operations with its own developer tools (`developer__write`, `developer__edit`, `developer__read`, `developer__tree`, `developer__shell` — namespaced names with documented input schemas). It does not delegate to the client fs server the way `opencode --pure` does, so the hub's enforcement posture is permission interception + hooks + bwrap (the Cline posture, plus hooks), not fs-server delegation. `AcpFsServer` stays wired (harmless if unused).

## 4. Per-runtime composition levers

- **`GOOSE_PATH_ROOT`** — overrides the root for ALL goose data/config/state (creates `config/`, `data/`, `state/` beneath it). This is the per-runtime isolation lever equivalent to the hub's `XDG_CONFIG_HOME` composition for OpenCode. Probe: honored by `goose acp`, config actually read from there.
- **`config.yaml`** — extensions are MCP servers (`builtin`, `platform`, `stdio`, `streamable_http`; SSE unsupported) with `envs`/`env_keys`, `available_tools` filtering, and timeouts. The hub can declare skills-mcp (and fs-exec-mcp) as a `stdio` extension in the per-runtime config — the F1 single-delivery-path mount. `permission.yaml` + auto-managed `permissions/tool_permissions.json` for granular tool permissions.
- **Provider composition (metering):** `GOOSE_PROVIDER`, `GOOSE_MODEL`, `GOOSE_PROVIDER__HOST`, `GOOSE_PROVIDER__API_KEY` (env > stored secrets) — the loopback metering proxy composes exactly as on the Cline/OpenCode paths: placeholder key inside the boundary, real key proxy-side. `GOOSE_DISABLE_KEYRING` for headless secret handling; provider env vars take precedence over stored secrets. Custom providers (`apiUrl`, `apiKeyEnv`, declarative store) are also first-class.
- **Control knobs:** `GOOSE_MODE` (env > config), `GOOSE_ALLOWLIST` (extension allowlist URL), `GOOSE_TELEMETRY_ENABLED=false` (opt-out), `GOOSE_MAX_TURNS` / `GOOSE_SUBAGENT_MAX_TURNS` / `GOOSE_MAX_BACKGROUND_TASKS`, `GOOSE_SEARCH_PATHS`, `GOOSE_MOIM_MESSAGE_TEXT/FILE` (persistent per-turn injected instruction — a hub-discipline injection channel), `SECURITY_PROMPT_*` (built-in prompt-injection detection, classic + optional ML classifier), OTEL observability with GenAI message capture.
- **Headless posture:** `goose run -t` / `--recipe` / `--no-session` is the documented non-interactive mode (GOOSE_CONTEXT_STRATEGY=summarize, GOOSE_DISABLE_SESSION_NAMING) — stock, no patch tax, unlike account-cloud Cline.
- **Skills:** goose supports SKILL.md-style skills natively ("sources"; project skills discovered under `{workingDir}/.agents/skills/` — the same path convention as the hub's skills directory and the agentskills.io standard). Hub policy: hub-composed workspaces carry no native `.agents/skills`, so skills arrive only through the mounted skills-mcp extension — the single-delivery-path holds; native discovery is documented as intentionally starved, not relied on.

## 5. Subagents and orchestration (G6)

- **Subagents are disabled in manual-approval, smart-approval, and chat modes; they run only in autonomous mode.** Under the hub's `GOOSE_MODE=approve`, spawning is fail-closed absent — the inverse of Cline (which spawned invisibly in every mode) and structurally safer than gating a live spawn path. The hub remains the conductor; goose-as-lead cannot self-spawn under enforcement. The probe verifies the delegate tool is absent-or-denied and that nothing spawns unprojected.
- **External subagents:** goose can run *other* agents (e.g. codex) as MCP-server subagents — a nested-agent pattern where the inner agent executes under its own policy, outside the hub's ACP permission surface. Hub policy: extension allowlist + hub-composed config means no external-subagent extension can appear in a runtime the hub composes; the probe verifies the composed config is the only source and guard classification denies unknown high-blast-radius tools.
- **Recipes/subrecipes/schedules:** repeatable ops workflows (the operator's sysadmin/DevOps use case) and cron-style scheduled recipes (goose-internal scheduling). Schedules are a process-classified capability from the hub's perspective — tool filtering or guard classification handles them; not in the first qualification slice.

## 6. General-purpose surface (operator context)

goose is not a coding-only agent: developer tools + terminal integration + desktop control (computer controller / Peekaboo) + a broad MCP extension ecosystem + recipes for repeatable operational workflows + mentor mode + local-inference models (privacy) + mesh LLM routing. This matches the operator's sysadmin/DevOps-plus-development workload better than a coding-first agent. Cost per `docs/HOST_ADAPTERS.md`: every high-blast-radius tool needs explicit guard classification before its integration claims complete enforcement coverage — goose's namespaced, documented tool schemas (`developer__shell`, `computercontroller__*`, …) make that classification work mechanical but non-optional.

## 7. Honest unknowns (probe-derivative — no claims without live runs)

1. Does `goose acp` honor `GOOSE_PATH_ROOT` and read config/extensions from it?
2. In `GOOSE_MODE=approve` over ACP, does every mutating tool call reach `session/request_permission` (given LLM-classified write detection)? How usable are the reject options, and are denials honored?
3. Do subagent-internal tool calls fire `PreToolUse` hooks (SubagentStart/Stop events confirmed absent)? — decides Cline-seam replacement candidacy.
4. Which channel carries `usage_update` (standard `session/update`, goose-custom, or both), and does the metered contained turn complete with only the placeholder credential inside the boundary?
5. `session/load` over a contained `goose acp` restart: transcript replay and model-context restore (G4).
6. Does the hub-written skills-mcp `stdio` extension mount and deliver (`list_skills` verbatim) under the composed config (F1/G3)?
7. Hook/plugin discovery paths under containment (scratch HOME; project-scope plugins in the workspace).
8. ACP SDK/version pin: which protocol revision v1.50.1 speaks; re-run trigger on version bump (ambient-PATH parity with the OpenCode probes).

## 8. Cline-seam replacement assessment

The SDK seam is retained for exactly one capability: host-hook interception with visibility into subagent-internal tool calls (`docs/ACP_DECISION.md`, alternatives). goose offers the first credible stock alternative: an ACP-native agent with a blocking, fail-closed-capable hook surface. **Staged criteria (the seam is not retired by this qualification):** (a) the hooks probe proves PreToolUse deny + `on_failure: block` works under containment; (b) the subagent-internal hooks probe resolves — if subagent tool calls do not fire hooks, goose closes nothing and the seam stays for that reason; (c) a daily-driver period on goose for the general-purpose/ops workload. Until all three, the Cline seam keeps its "working tree, not an archaeology project" status and stays continuously exercised.
