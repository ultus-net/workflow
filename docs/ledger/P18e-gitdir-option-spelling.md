### P18(e) - The inspectable git command-option gitdir spelling (`--git-dir=`, `--git-dir <path>`, `--work-tree`) joins the direct-write gate (2026-09-30)

**Source:** The P18(d) fragment's recorded boundary (a bare repo / explicit gitdir "is reachable only when also env-spelled") and the P18(c) boundary ("a gitdir not named `.git`"); SECURITY_ASSURANCE residual #21's recorded still-open slice; GitHub issue #296. Dispatched as a subtask of the 2026-09-30 P18 wave, branch `feat/p18-gitdir-spelling` off origin/main.

**What landed.** The P18(c)/(d) classifier reached an explicit gitdir through two routes: a literal `.git` path component and the command *environment* (`GIT_DIR=…`, `GIT_COMMON_DIR=…`, `GIT_WORK_TREE=…`). Git also names the gitdir as **its own top-level command option** — `git --git-dir=<path>`, the separate `git --git-dir <path>`, and their `--work-tree` twins — which carries no `.git` component and no env assignment, so it was invisible to the gate. One classifier, one extension:

- **The option-spelling scan.** `gitDirSpellingsIn(command)` (`git-policy.ts`) now also scans a `git` invocation's surviving command words (after the wrapper/assignment prefix is unwrapped, so `sudo git --git-dir=…` is covered) for `--git-dir=<path>` / `--git-dir <path>` and `--work-tree=<path>` / `--work-tree <path>`, pushing the value alongside the env spellings. `directRefWriteTargetIn(path, { gitDirs })` then classifies a write under the named gitdir with the SAME shared tail logic: a `refs/heads/<branch>` tail resolves to the branch name (protected denies with the target named, feature ref keeps the allow), a ref-adjacent tail with no resolvable branch fails closed, and non-ref content stays outside the branch-target gate. `--work-tree` rides the same conservative lean the env route recorded (`GIT_WORK_TREE=`).
- **The ref-adjacent command form is unchanged and already covered** by the W101 target gate: `git --git-dir=/tmp/bare update-ref refs/heads/main …` normalizes past the leading option and denies via the update-ref parser; the new pins record it.

**The file_write-lane aliases (assessed, no behavior change).** The `file_write` lane (`policy.ts`) carries a path and optional patch text — **no command text**, so neither the env spelling (P18(d)) nor the command-option spelling (this round) can be derived there. The lane keeps the `.git`-component route it *can* inspect (P18(c)); a bare-gitdir path with no `.git` component stays outside the gate on that surface. There is no other in-command alias to derive (there is no command), so the boundary is recorded rather than pretended — and it is pinned as an executed allow in the P18(e) test block.

**Boundaries (remain, recorded honestly):** a `.git` symlink hop whose write spelling carries no `.git` component; a gitfile working directory (`.git` is a file naming its gitdir); an unresolved/globbed gitdir spelling (env or option — the value is dropped downstream, so only a `.git` component still classifies, while an unresolved PATH under a literal gitdir fails closed); the `file_write` lane's lack of command text (above); and non-ref `.git` content (objects, index, config, hooks, refs/tags — a different policy surface). A git invocation where `--git-dir` is not a real top-level option (e.g. quoted argument data) is read lexically as a gitdir spelling — a deny-leaning false-positive class, consistent with the conservative lean; it can add a deny, never loosen one. These stay recorded, not pretended.
