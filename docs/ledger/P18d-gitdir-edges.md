### P18(d) - The inspectable env-spelled gitdir route joins the P18(c) direct-write gate (2026-09-30)

**Source:** PARKED_AND_LIMITATIONS.md row P18's recorded boundary from the P18(c) entry ("a gitdir NOT named `.git` (a bare repo or a `GIT_DIR`-spelled directory)", "a case-variant `.GIT/` path"); SECURITY_ASSURANCE residual #21's RESOLVED PART 2 boundary; GitHub issue #296. Dispatched as a subtask of the 2026-09-30 P18 wave, branch `feat/p18-gitdir-edges` off origin/main.

**What landed.** The P18(c) classifier required a literal `.git` path component, so a bare repo or a `GIT_DIR`-spelled directory — whose ref-adjacent writes carry no `.git` — was invisible to the branch-target gate. Two inspectable extensions, one classifier:

- **The env-spelled gitdir route.** `gitDirSpellingsIn(command)` (`git-policy.ts`) extracts the gitdir spellings a command names through its environment in command position — `GIT_DIR=…`, `GIT_COMMON_DIR=…`, `GIT_WORK_TREE=…` — including after `env`/`export` options and across `;`/`&&` segments (`export GIT_DIR=…; echo …`), so argument data (`echo GIT_DIR=/x`) is not mistaken for a live assignment. `directRefWriteTargetIn(path, { gitDirs })` then treats a write under one of those directories as ref-adjacent and classifies its tail with the SAME shared logic (`refTailTarget`): a `refs/heads/<branch>` tail resolves to the branch name (protected denies with the target named, feature ref keeps the allow), a ref-adjacent tail with no resolvable branch (`packed-refs`, `HEAD`, `logs`, the `refs`/`refs/heads` directory, the gitdir itself) fails closed, and non-ref content (`index`, `objects`, `config`, `refs/tags`) stays outside the branch-target gate.
- **The `.git` component match is now case-insensitive**, so the case-variant `.GIT/` path (the same directory on a case-insensitive filesystem) classifies identically. The branch tail stays case-sensitive (git branch names are); lexical `.`/`..` collapse is preserved with the leading `/` kept so an absolute path and a relative spelling cannot collide.
- **Two surfaces, one classifier (unchanged wiring).** The shell mutation extractor (`boundary-policy.ts`'s `checkBoundaryPolicy`) computes the command's gitdir spellings once and passes them to every target; `boundary-policy` imports `gitDirSpellingsIn` from the gate file (no import cycle). The `file_write` lane (`policy.ts`) has no command, so it keeps the `.git`-component route only (the env spelling is not available on that surface).

**Review round (2026-09-30).** The five-axis review's P2: the P18(d) env-gitdir route was bypassed by wrapper prefixes and by the `sh -c` recursion. (1) `gitDirSpellingsIn` recognized only `env`/`export` as command-position prefixes, so `sudo GIT_DIR=/x echo … > /x/refs/heads/main` (and the `doas`/`command`/`nohup`/`nice`/`timeout`/`stdbuf`/`time` forms) yielded no gitdirs and allowed, while the literal `.git` spelling denies. (2) `gitDirs` was not threaded into the nested-shell recursion, so `GIT_DIR=/x sh -c '… > /x/refs/heads/main'` allowed against the pinned P18(c) wrapper-transparency cell. Both closed: `gitDirSpellingsIn` now scans the wrapper/assignment prefix through the shell lane's own `unwrapWordsWithPrefix` (single-sourced wrapper vocabulary; `export` stays an explicit builtin drop), and `checkBoundaryPolicy` carries an `inheritedGitDirs` union into the recursive call. The recorded "unresolved PATH under a literal gitdir fails closed" claim is now PINNED and executed: a globbed tail fails closed on `protected-branch-write`; a `$VAR` tail is denied earlier by the boundary lane's `guard-tamper`, also fail-closed, recorded under its actual policy. **Boundaries (remain, recorded honestly):** a `.git` symlink hop whose write spelling carries no `.git` component (resolving the symlink is a filesystem fact the lexical classifier does not read — a `.git` component that IS spelled classifies as before, and the env route above is the inspectable substitute when the gitdir is named explicitly); a gitfile working directory (`.git` is a file naming its gitdir — `.git` itself fails closed, the named gitdir is reachable only when also env-spelled); an unresolved or globbed gitdir spelling (`GIT_DIR=$X`, `GIT_DIR=*` — dropped, since it cannot be matched; an unresolved PATH under a literal gitdir fails closed); and non-ref `.git` content (objects, index, config, hooks, refs/tags — a different policy surface: `.git/config` would need an alias/hooks rule, not branch-name targeting). These stay recorded, not pretended.

**Boundary refine (2026-09-30, issue #296; branch `feat/p18-boundary-refine`).** Dated re-assessment of the recorded edges; one spelling landed, the rest stated.

- **LANDED — the in-command `.git` symlink hop.** The recorded symlink boundary narrows to the case where the target is a PRE-EXISTING filesystem fact: when the COMMAND itself spells the hop's target (`ln -s <ref-adjacent> <link>`), the link is lexically resolvable. `refSymlinkAliasSpellingsIn` (git-policy) returns such alias prefixes via a bounded fixpoint (a chained alias `ln -s <gitdir> a; ln -s a b` resolves); `directRefWriteTargetIn` classifies a write STRICTLY UNDER an alias by the same tail logic (the link path itself is not the gitdir, so creating the alias stays allowed). The shell lane passes `{ gitDirs, gitDirAliases }`; a nested `sh -c` inherits both (union, deduped). The fixpoint resolves aliases whose target is a `.git`-component ref path or a directory named by the command's gitdir spellings. Red-first 119 policy tests / 118 pass / 1 fail (the alias deny block; the feature-target allow, the non-ref/pre-existing-alias allows, and the already-landed P18(d) over-deny pins held as-found) → green 119/0; app `tsc --noEmit` exit 0.
- **RECORDED — the `.GIT` over-deny is intentional.** `.GIT/refs/heads/main` and `x/.GIT/refs/heads/main` deny even on a case-sensitive filesystem, where `.GIT` may be a benign directory: the lexical classifier cannot distinguish the filesystems and the guard fails closed. Deliberately NOT loosened for a real gitdir's `.Git`/`.GIT` variants (pinned). Non-ref `.GIT` content stays allowed.
- **RECORDED — `GIT_WORK_TREE` is conservatively a gitdir spelling.** It names the WORK TREE, not the gitdir; it is kept because a worktree path can sit adjacent to (or contain) a gitdir and the read is lexical. A protected ref tail under it over-denies (pinned); non-ref content under it is untouched. Stated as a conservative over-approximation, never a semantic claim that the worktree is the gitdir.
- **RECORDED — a gitfile's content path stays un-inspectable.** The classifier never reads file bytes; the named gitdir is reachable only when also env-spelled (as-found pin). A newly-NOTED inspectable spelling — `git --git-dir=…` naming a gitdir in the same command — is outside this iteration's recorded-edge scope and left for a follow-up.

> **Dated review-round note (2026-09-30):** the five-axis review noted the `file_write` lane does not receive the derived gitdir aliases (it has no command text to derive them from — the alias is lexical to the command that spells the `ln -s`), so the new in-command symlink-hop classification applies to the shell mutation lane only; a `file_write` under a command-created alias stays with the outer containment. Recorded as the honest completeness boundary, not a regression.
