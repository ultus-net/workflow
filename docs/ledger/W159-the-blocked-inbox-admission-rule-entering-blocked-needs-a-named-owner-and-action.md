### W159 - The blocked-inbox admission rule: entering blocked needs a named owner + action; agents may only name themselves (Planned - kernel-change-first, the borrowings spec's strongest unbuilt idea) (2026-09-27)

**Source:** the borrowings spec's blocked-inbox idea, queued by the operator across the wave sessions. Verified 2026-09-27 on main@5e5d7ef: the kernel derives BLOCKED purely from dependency readiness (`src/kernel/task-graph.ts:487-500` `#recomputeReadiness` — `ready ? "READY" : "BLOCKED"`; the transition table admits READY→BLOCKED only through that recompute, `src/kernel/task-graph.ts:17-22`), so a task blocked for a REASON (awaiting an operator decision, an external dependency, a named unblocker) has no canonical home: the reason lives in run-registry blocking reasons or prose, invisible to the kernel's own graph.

**The design (captured before code, per the kernel-change-first discipline):**

- Kernel contract: `WorkflowTask` gains an optional actor-initiated blocked record — `{ owner: ActorId, action: string, reason?: string, enteredAt: string }` — plus a legal transition `IN_PROGRESS|READY → BLOCKED` that REQUIRES the record (admission fails closed without a named owner + action).
- The self-naming rule: an agent-context caller may only set `owner` to itself (the W157 attribution's actor vocabulary is the join; a scheduler-origin caller names the schedule; the operator surface names the operator). Anything else is refused — an agent cannot volunteer another actor to unblock it.
- Exit stays evidence-gated: `BLOCKED → READY` keeps today's dependency-derived readiness AND requires either the named owner's action consumed (one-shot consumption, the W112 grant-lifecycle shape) or the dependency graph resolving on its own (the record then renders as stale context, not a live block).
- The blocked inbox on the surfaces (the W150 posture-strip pattern): a projection of actor-initiated blocked records grouped by owner, each row rendering the named action — the operator sees exactly who owes what.

**Acceptance criteria (not started):**
- [ ] The kernel refuses an actor-initiated BLOCKED without owner+action and refuses an agent-named foreign owner (focused pins on the transition table + the admission rule).
- [ ] The exit path consumes the named action one-shot; the dependency-derived exit stays automatic (pins both ways).
- [ ] The posture strip renders the inbox (owner-grouped, named actions, honest empty state).
- [ ] Kernel purity holds: the record is caller-supplied data, no clock reads, no actor vocabulary invented inside the kernel.

**Residuals (cut):** scheduled auto-unblock dates, cross-task owner delegation chains, a notification channel — none of the borrowings spec's cut lines move.

**2026-09-27, kernel slice landed** (branch `feat/w166-blocked-admission-kernel`, based on origin/main a7dc008; W166, GitHub issue #318 — the borrowings spec's W166 line, kernel-change-first). The design fragment above is now a kernel transition contract; acceptance criteria 1, 2, and 4 are met with focused pins (`test/blocked-admission.test.ts`, 18 tests: red-first 17 fail / 1 green guard on the unmodified tree, 18/18 green after; held-out kernel suites task-graph + task-graph-invariants 19/19 and persistence + application + activity-timeline 42/42, unmodified; lint + typecheck exit 0). What the kernel now does:

- `WorkflowTask.blocked?: BlockedRecord` (`src/kernel/contracts.ts`): `{ owner, action, reason?, enteredAt }`, the owner typed as the **existing W157 attribution vocabulary** (`TransitionAttribution["actor"]` — no new vocabulary invented), `enteredAt` caller-supplied (no clock read), the record plain caller data (defensively copied at admission/construction, like `dependencies`).
- **Admission** (new table edges `IN_PROGRESS|READY → BLOCKED`): requires the record (fail closed without → `BLOCKED_RECORD_REQUIRED`; malformed → `BLOCKED_RECORD_MALFORMED`) and the caller naming ITSELF as owner — `owner === attribution.actor` against the W157 vocabulary, refused otherwise (`BLOCKED_OWNER_MISMATCH`; no attribution → `BLOCKED_OWNER_UNVERIFIED`). A record on any other transition is refused, not dropped (`BLOCKED_RECORD_MISPLACED`) — the `FAILED → BLOCKED` retry path stays recordless and ungated.
- **The record holds the block**: `#recomputeReadiness` no longer exits a BLOCKED task on dependency readiness alone when a live record holds it — this is what makes a `READY → BLOCKED` admission stick instead of being instantly reverted. The automatic dependency-derived exit stays exactly as today for recordless tasks.
- **Exit, two ways** (as the design line says): (1) the **named owner's action consumed one-shot** — the explicit `BLOCKED → READY` transition (new table edge) requires the live record, dependency-derived readiness still gate (`DEPENDENCY_READINESS_REQUIRED` without), and the owner's own attribution (`BLOCKED_OWNER_MISMATCH`/`BLOCKED_OWNER_UNVERIFIED` otherwise); on success the record is REMOVED (the W112 grant-lifecycle shape — `BLOCKED_EXIT_WITHOUT_ACTION` if there is nothing to consume); (2) the **dependency graph resolving on its own** — readiness flipping false→true while the record is live (kernel-private per-pass signal) auto-exits the block and the record STAYS on the task as stale context, not a live block.
- **Stated interpretation (strong-only disclosure, not a silent deviation):** "the dependency graph resolving on its own" is implemented as the readiness false→true flip under a live record. A record admitted while the dependencies were ALREADY all VERIFIED (the record being the sole blocker) therefore holds until the owner's action, or until a later dependency cycle (invalidation then re-verification) makes the graph resolve under it — an unrelated dependency cycle releases the record to stale context. This reading needs no kernel-managed liveness flag on the caller-data record and is restore-consistent: a resolved record-block can never be persisted (the resolution exits in the same recompute pass that observes it), so every persisted `BLOCKED`-with-record task restores as held. **Also stated:** the explicit exit verifies the CONSUMER is the named owner (the design's "the named owner's action consumed" read strictly — an agent-named block cannot be consumed by another actor).
- **Kernel purity holds:** no clock reads (`enteredAt` caller-supplied and pinned round-tripping verbatim), no IO, no new actor vocabulary, no host/SDK imports.

**Named next slice (NOT in this PR): the blocked-inbox projection** — the W150 posture-strip pattern rendering actor-initiated blocked records grouped by owner with the named action per row and an honest empty state, plus the board's `blocked` column projecting the kernel record (the borrowings spec's W166 UI half: "the UI renders the unblock descriptor from the record, never synthesized"). The kernel record is in place for it; a record on a non-BLOCKED task renders as stale context there.
