### W175 - Runs page + run detail panel — the flagship gap's UI phase (2026-09-30)

**Source:** the hub-dashboard redesign spec's "Runs page + run detail (Section 2, approved — the flagship gap)" (`docs/superpowers/specs/2026-09-29-hub-dashboard-redesign-design.md:118`), queued as GitHub issue #346, phase 2 of the approved sequencing (the `/api/runs` relay itself was slice 1, see `docs/ledger/W175-runs-relay.md`; the shell + Overview landing was W174 / PR #350). The brief: every registry run one row each, a five-tab detail panel, ONE status vocabulary, and the red-first pin set.

**What landed:**

- **The Runs page** (`src/ui/webapp/runs-view.tsx`, new): one row per registry run — mono run id, title, origin attribution, state, work-product link, recorded cost, start — with filters (origin, state) derived from the records themselves (`filterRunRows`/`runFilterChoices`/`originBucket`, exported pure for the pins). A row without a `startedAt` record renders "no recorded time"; no duration renders anywhere (the relay carries no duration record and the view never derives one from kernel transitions). Origin attribution renders VERBATIM from the origins record via `formatRunOrigin` (presenters.ts) — an unattributed run renders "origin not recorded", and a source pin holds that the view never parses run ids for attribution (the W153 rule). Empty table names the first action ("no runs recorded yet — delegate a board task or fire a schedule"); the unanswered/predates-relay states render their named absences ("state unavailable — the runs relay has not answered" / "runs relay unavailable (<reason>)").
- **The run detail panel** (`src/ui/webapp/run-detail-panel.tsx`, new): header (run id, state, origin, workspace only when the record carries one, recorded start) + Summary / Timeline / Evidence / Review / Cost tabs, all five present in the document (inactive ones `hidden`). Summary: usage labelled *recorded*, house $/toFixed(4) cost, the cache read/create pair with the recorded lane asymmetry named verbatim ("on the OpenAI chat-completions lane both stay 0 (its cached reads are inside promptTokens)"), the completion claim with its verified-at-claim flag BESIDE it, the work-product reference with the W167 liveness pill derived only from the recorded provider read (no record, no pill). Timeline: the timeline lane's rows that NAME the run (boundary-checked `timelineRowsForRun` join, no prefix collisions) plus the row's own `startedAt` begin record and the retention line verbatim. Evidence: the relay's records whose subject IS the run id (`evidenceRowsForRun`), rendered through the shared W158 row renderer with every non-ready preview state named. Review: verdict + summary + admitted/not-admitted verbatim, blocking reason verbatim, the reasoning-claim monitor with `recall`/`timeToResponseMs` rendered as `unmeasured`. Cost: the full `RunUsageSummary` raw. Every absent family renders its named absence — never a fabricated panel.
- **The one status vocabulary** (`src/ui/webapp/presenters.ts`): `STATUS_TOKENS` + `statusToken()` — the task/run/freshness class-token map used identically in badges, rows, cards, and feeds. Mechanical rename only (the rendered class strings are byte-identical with what the views rendered before): `app.tsx`'s two `task-state-*` sites and `overview-view.tsx`'s `status-dot` site now derive through it, and the source pin holds that no `state.toLowerCase()` derivation remains in any view.
- **One mirror for the runs lane** (`src/ui/webapp/runs-record.ts`, new): the full `RunsRecordState` mirror (all ten record families) + `useRunsRecord()`, MOVED out of overview-view.tsx so Overview, Runs, and the detail panel read one definition; overview-view imports it.
- **The W158 evidence primitives' shared home** (`src/ui/webapp/evidence-preview.tsx`, new): `artifactKind`, `EvidenceStripRow`, the named `EvidenceContentPreview` states, `HubEvidenceRow`, `useHubEvidence`, and `useContentPreviews` moved out of app.tsx so the detail panel's Evidence tab reuses them without an app.tsx import cycle; app.tsx re-exports the pinnable surface so `test/webapp-surface.test.ts` imports stay byte-stable (45/45 unchanged).
- **The detail opener memory** (`src/ui/webapp/run-detail-state.ts`, new): `{ opener, runId }` under `workflow.runs.detail` in sessionStorage, the rail-state.ts two-shape guarded pattern (access-time + call-time denial, corrupt records dropped, opener validated against the shell's views). app.tsx mounts the panel in the shell's right-side contextual region (`runs-detail`), opens it from a row click, closes it on Esc (the panel owns Escape while open, after chrome, before turn-cancel) or the "back to <opener>" affordance — focus returns to the invoking row and the view returns to the opener page.
- **Styles** (`src/ui/webapp/styles.css`): the runs table, filters, detail panel, tabs, and absence registers in the token system; square edges (radius untouched, the sharp-edges pin still passes), mono machine values.

**A recorded decision (do not reverse without a record change):** the detail panel's Timeline tab does NOT join the lane's kernel transition rows per run — W152's `TimelineRow` carries no task id, and the kernel rows' summaries join only by task TITLE (ambiguous across runs with equal titles), so a per-run kernel join would fabricate attribution. The tab renders the registry rows naming the run + the begin record, and states the boundary in the panel verbatim ("kernel transition rows are not joined per run — the timeline lane's rows carry no task id (W157 is the record change that would add one)"). Similarly, the Evidence tab claims only records whose subject equals the run id — the relay's records carry no other run linkage, and the workspace-test-subject records are honestly not claimed (the panel says so).
