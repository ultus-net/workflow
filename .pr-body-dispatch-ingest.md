## Summary

Task 4 of the C1 Azure control-plane deploy plan (`docs/ledger/control-plane-c1-deploy-plan.md` §2.c; decisions D1 dispatch-owner=hub, D3 Storage Queue + blob ref) — **the return leg**. Task 4 built the enqueue seam (a validated request becomes one queued worker-job message). This change closes the loop: it records what each dispatched job DECLARED it would produce, then ingests the worker's returned evidence blob and checks that the declaration is actually covered.

Spec §6:126-130: "Evidence freshness … stays hub-owned; a run that returns without declared evidence does not advance state." The registry is the denominator: without a hub-held record of what was dispatched, a caller could self-satisfy its own coverage check — so the record is written by the hub's own enqueue wrapper, never supplied by the client.

### New module: `src/integrations/azure-jobs-record.ts`
- **The dispatch-record registry** (`createDispatchRecordRegistry`) — the hub-held denominator. On enqueue it records `declaredEvidence`, the corpus fingerprint, the evidence blob path, and the container. Bounded (64): the lookup map and the two journals evict oldest-first; an evicted task validates as `unknown` (honest, never a fabricated pass).
- **`validateWorkerEvidence`** — the structural intake for the worker's returned evidence blob (the result record `images/worker/run.mjs` uploads).
- **`createAzureJobsIngest`** — the `validateDispatch(taskId)` closure with the fail-closed outcome matrix: `unknown` (no record, never hits the network), `missing` (blob 404), `invalid` (structural fault or a returned `taskId` that disagrees with the requested one), `incomplete` (a declared evidence name is absent, named in the reason), `stale-corpus` (fingerprint drift), `failed` (nonzero worker exit), otherwise `covered`. Every resolved outcome is journaled; a non-404 transport fault THROWS so the route 5xxs. REST only, no Azure SDK — the same shared Bearer chain as the enqueue client.
- **`createRecordingEnqueue`** — wraps the enqueue closure so a successful dispatch is recorded; a failed enqueue records nothing and a malformed message keeps its `AzureJobMessageError` (the 400 classification).

### Hub route: `POST /dispatch/azure-job/validate`
`hub-http.ts` + `workflow-hub.ts` + `cli/hub.ts`: operator-token class; capability withheld → 404; missing taskId → 400; a resolved outcome → 200; a transport fault → 5xx. A malformed taskId is a typed `DispatchRequestError` (400) — classified by type, never by message prefix, because a Node fetch transport failure is itself a `TypeError`. The composition root builds one registry shared by both legs.

### Design decisions recorded
- **Registry-as-denominator.** The hub records the declaration at enqueue and the ingest checks the returned blob against that record. The alternative (the client supplies expectations) would let the caller self-satisfy the check.
- **The record is the single source of truth for where evidence lives.** The ingest reads the container from the record, not a separately configured option, so a job's declared location is authoritative.
- **`taskId` binding.** The returned blob's `taskId` must match the requested one — a blob for task A cannot satisfy a validate for task B.

## Review
Independent five-axis review recorded (APPROVE) at `21cd1612`. The review rounds drove:
- **P1/P2** — the returned evidence record's `taskId` is now checked against the requested one (mismatch → `invalid` with a named reason); a blob for task A cannot satisfy a validate for task B.
- **P3** — the registry's primary lookup map is bounded at the same 64 limit with oldest-first eviction (not just the journals), re-inserting on re-record so the freshest task survives.
- **P3** — the route's 400 classification is a typed `DispatchRequestError`, replacing a message-prefix check that would misreport a `TypeError` transport fault.
- **P3** — `AzureJobsIngestOptions.evidenceContainer` stored-but-unread is dropped; the record is the single source of truth.
