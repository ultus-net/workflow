# Verification Accountability MCP

Durable, bounded references to verification observations for cross-session engineering handoffs. This server delegates test execution, CI lookup, and browser verification to Test Intelligence, CI Intelligence, and Browser Verification; it is not a test runner, CI provider client, or browser itself.

`record_verification` accepts a bounded Test request, a provider-qualified CI run ID, or a bounded browser verification request (URL plus assertions), then calls the configured primitive MCP itself. Callers cannot submit result payloads. Stored `observation` records therefore summarize data returned on the trusted primitive connection rather than promoting agent prose or caller-created Test/CI/browser-shaped JSON. Configure primitive commands with `VERIFICATION_ACCOUNTABILITY_TEST_COMMAND` / `VERIFICATION_ACCOUNTABILITY_TEST_ARGS`, `VERIFICATION_ACCOUNTABILITY_CI_COMMAND` / `VERIFICATION_ACCOUNTABILITY_CI_ARGS`, and `VERIFICATION_ACCOUNTABILITY_BROWSER_COMMAND` / `VERIFICATION_ACCOUNTABILITY_BROWSER_ARGS`; CI repository identity comes from the same `CI_GITHUB_REPOSITORY` configuration used by CI Intelligence, and Browser Verification inherits its `BROWSER_VERIFICATION_*` connection configuration.

`list_verifications` returns at most 20 observations by default and 50 explicitly. CI observations are `fresh` or `stale` only when compared with the same provider/repository revision scheme. Browser observations carry the page identity the browser tool observed (`browser_page` url plus page hash) and a `browser_verification` source recording the observed-at time and the Browser Verification capability; they are `fresh` only when a caller-supplied current page identity has the same URL and page hash, `stale` for the same URL with a different page hash, and `unknown` otherwise. A different provider/repository, a local fingerprint, or no comparable subject yields `unknown`. Local Test Intelligence records use an explicit `local_test_execution` subject whose content subject is `unavailable`: the authority establishes execution workspace and outcomes but not a content-sensitive subject stable throughout execution, so content freshness remains `unknown` even if a caller measured a worktree fingerprint before or after the run.

Failed, timed-out, cancelled, and truncated observations remain visible evidence; they are never converted into success. A `truncated` result cannot establish that omitted checks passed. Records are isolated by canonical workspace, persisted atomically under `VERIFICATION_ACCOUNTABILITY_DATA_DIR` (or the platform data directory), and bounded to 500 observations / 5 MiB per workspace store. Recognizable secret-bearing provenance is rejected.
