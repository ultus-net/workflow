# Git Intelligence Contract

## P401 Scope

Stage 4 starts with structured local working-tree state, followed by bounded diffs and local history. The domain is read-only: it does not stage, commit, restore, fetch, push, invoke a forge, or accept arbitrary Git arguments. Changed-symbol correlation remains cross-domain work and is not part of the Git product contract.

The first implementation targets the installed `git` executable and Git's stable machine-readable interfaces. In particular, working-tree parsing should use porcelain v2 with NUL-delimited paths rather than human-readable status output. The Git documentation guarantees porcelain formats for scripting and notes that porcelain v2 tracked-entry order is undefined, so the adapter must normalize and sort results itself.

## Domain Boundary

A Git adapter owns process invocation, Git-output parsing, normalization, confinement, cancellation, and output bounds. MCP owns input/schema validation and maps normalized domain errors to tool errors; it must not parse Git output or construct caller-controlled Git command lines.

Every operation receives an absolute `workspaceRoot`. The adapter canonicalizes both `workspaceRoot` and the Git worktree root returned for that same directory, then requires those canonical filesystem locations to be identical. A directory merely contained by a parent repository is rejected rather than silently widening authority to Git metadata or paths above the granted workspace. Bare repositories and paths that are not worktrees are outside the initial contract. Nested repositories can be queried only by explicitly supplying that nested worktree as `workspaceRoot`.

All public paths are normalized workspace-relative paths. Returned repository paths must remain within the canonical worktree after path normalization. Operations that accept a file path additionally realpath existing working-tree files before host-filesystem access; symlink targets outside the workspace are rejected. Git identities for deleted or historical paths are lexical repository paths and are never used as permission to read an external filesystem target.

## Process Safety

The adapter invokes only fixed, product-owned Git subcommands and flags. It never uses a shell, caller-provided arguments, aliases, editors, pagers, credential helpers, remote transports, package scripts, or repository hooks as an execution mechanism.

Inspection commands must be non-interactive and must avoid optional repository mutations. In particular, status uses Git's no-optional-locks behavior because Git documents that ordinary status may refresh and write cached index stat information. Every inspection command that can demand repository objects must disable Git lazy fetching so a partial/promisor repository cannot turn a local object read into remote transport. The implementation must neutralize configuration-driven execution relevant to each chosen inspection command, including FSMonitor for working-tree status and external diff/text conversion for diff operations, rather than inheriting repository-configured executable behavior. Pagers are disabled explicitly. The command policy must state which configuration scopes remain readable and override every execution-capable setting reachable by the selected command; it must not rely on the ambient system/global/local/worktree configuration being benign. The child environment is product-controlled and excludes credential-bearing and Git command-injection variables such as `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG*`, `GIT_EXTERNAL_DIFF`, `GIT_DIFF_OPTS`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_SSH_COMMAND`, and inherited lazy-fetch controls. Product-owned invocation then supplies its own no-lazy-fetch policy rather than trusting inherited environment state.

This is process hardening, not a sandbox. Git necessarily reads repository-controlled data and working-tree metadata with the server's OS identity. Malformed or hostile repositories therefore remain subject to Git's own parser/security model.

## Working-Tree Status

The first public capability returns one normalized entry per changed repository path. Each ordinary tracked entry contains `path`, optional `originalPath` for a rename/copy, and normalized staged and unstaged states. The normalized change vocabulary is `added`, `modified`, `deleted`, `renamed`, `copied`, `type_changed`, `unmerged`, `untracked`, and `none`; unknown future porcelain status values are errors rather than silently misclassified changes. Porcelain-v2 `u` records are distinct: their `XY` pair describes the two merge heads relative to the merge base, not ordinary index-versus-`HEAD` and worktree-versus-index states. An unmerged entry therefore reports staged and unstaged as `unmerged` and carries a separate normalized conflict kind for the supported porcelain pairs `DD`, `AU`, `UD`, `UA`, `DU`, `AA`, and `UU`; unsupported future unmerged forms are errors rather than being interpreted through ordinary `X`/`Y` semantics.

Ignored files are excluded. Untracked files are requested individually rather than collapsed to directory names. Rename detection is explicitly enabled with a product-owned policy so user configuration cannot decide whether an equivalent fixture appears as delete/add or rename. Submodule state may be exposed later as separate normalized metadata; P403 must not flatten recursive submodule dirtiness into ordinary file changes as though it described the superproject path itself.

Entries are sorted lexically by normalized `path`, then `originalPath`, independent of Git's output order. The public query accepts a positive `limit`, default 100 and maximum 500. The result contains `entries` and `truncated`; `truncated` is true only when at least one additional permitted normalized entry was observed.

A clean worktree is a successful empty result. A non-repository workspace, a workspace whose discovered worktree root differs from `workspaceRoot`, malformed/unsupported Git output, spawn failure, or confinement violation is a domain error.

## Diff Contract

P404 will expose only explicit product-defined scopes: `unstaged` means working tree versus index, and `staged` means index versus `HEAD` (or the empty tree for an unborn repository). Callers do not provide revisions, pathspec magic, diff drivers, or arbitrary options.

Results normalize file change metadata separately from bounded textual hunk evidence. Binary changes are represented structurally without pretending binary content is text. Rename source/destination paths are preserved. Product-owned diff invocation disables external diff/text-conversion execution and does not depend on pager, color, or user diff formatting. P404 accepts a positive file `limit`, default 100 and maximum 500. Textual patch evidence is bounded to 32 KiB of UTF-8 per returned file and 256 KiB across the result. Each file carries `patchTruncated`, and the result carries `truncated` for omitted permitted files plus `evidenceTruncated` for omitted textual patch evidence; each flag is true only when additional corresponding evidence was observed. Binary files carry no textual patch evidence.

## History Contract

P405 provides bounded local provenance for an explicitly confined workspace-relative file. Blame/history reads only already-present local objects and never fetches missing history. `file_history` defaults to 50 commits and permits at most 200; each commit exposes at most 8 KiB of UTF-8 subject/body evidence with a per-record `messageTruncated` flag. `file_blame` defaults to 200 lines and permits at most 1000. Both results expose `truncated` only after observing an additional permitted record or line.

History commands use machine-oriented formats with explicit product-owned fields. Caller-supplied revision expressions and arbitrary Git format strings are excluded initially. Public paths are non-empty workspace-relative lexical paths without traversal; Git receives them as literal paths rather than pathspec expressions. `file_history` follows whole-file renames and preserves the path identity reported for each change. `file_blame` reads committed `HEAD` provenance, follows Git's whole-file rename attribution, and returns the attributed historical path and 1-based original/final line numbers. Historical paths remain lexical Git identities and are never dereferenced as host filesystem paths.

`file_history` explicitly disables external diff and text-conversion execution. Git blame does not provide equivalent reliable disable switches for every repository-configured diff/textconv mechanism, and configured ignore-revision files can alter attribution before command-line clearing takes effect. Production Git children disable system configuration and point the global configuration scope at the platform null device; `file_blame` then inspects the remaining repository-local and worktree configuration with a fixed read-only command and fails closed when `diff.external`, any `diff.<driver>.textconv`, or `blame.ignoreRevsFile` is present. It never executes those configured behaviors.

## Cancellation, Bounds, And Errors

Every Git subprocess accepts an `AbortSignal`. Cancellation must terminate the direct Git child and wait for exit/resource cleanup before returning. Because initial inspection commands do not intentionally create descendants, portable descendant-tree termination is not claimed; any command that introduces such behavior requires a new process-lifecycle review.

P403 status is bounded by the 100-default/500-maximum entry limit above. Git output itself must also have an internal byte ceiling so a malicious or unexpectedly large repository cannot force unbounded buffering before normalization; P403 must choose and test that ceiling while preserving the rule that public `truncated` describes omitted permitted records, not a parser failure. Exceeding an internal parse-safety ceiling before the adapter can establish complete record boundaries is a domain error rather than a partial result presented as complete.

Malformed MCP input is rejected at the MCP boundary. Git executable absence, unsupported Git behavior, repository mismatch, confinement violations, malformed machine output, cancellation, and process failures are normalized domain errors. Expected repository states such as a clean worktree or an unborn `HEAD` are successful results when the requested operation defines their semantics.

## Deterministic Repository Fixture

P403-P405 use product-local temporary Git repositories created by fixed test setup, not this repository's history. Fixtures set repository-local author identity and create commits with fixed author/committer names, email addresses, and timestamps so expected object/history output is reproducible. Tests invoke Git directly with explicit arguments to construct fixture states; fixture setup is test infrastructure, not part of the production adapter.

The fixture matrix must cover clean state; staged and unstaged modifications; a path with both staged and unstaged changes; individually reported untracked files; additions and deletions; detected renames with source/destination identity; unmerged/conflict state; unusual valid filenames handled through NUL-delimited parsing; an unborn repository; a nested repository; a workspace that is merely a subdirectory of a parent repository; and a non-repository directory. Diff fixtures additionally cover text additions/modifications/deletions, staged versus unstaged scope, rename metadata, binary content, and output bounds. History fixtures additionally contain multiple fixed commits and a rename so blame/log provenance can be asserted without network access.

Confinement tests include traversal input, a workspace root reached through a filesystem symlink/alias whose canonical location is the Git worktree root, and a working-tree symlink whose target is outside the canonical workspace. The symlink fixture separately proves that an operation requiring host-filesystem access rejects the outside target while historical Git path identity remains lexical and does not dereference that target. Safety tests configure reachable execution mechanisms as sentinel commands and prove supported inspection never executes them: FSMonitor for status; pager and external diff/text conversion where the selected commands could consult them; a repository `core.hooksPath` containing sentinel hooks whose marker must remain absent across every supported inspection; and a credential helper/remote sentinel in a partial/promisor-repository case that proves missing objects fail locally rather than triggering lazy fetch. The production command matrix records the explicit flags/config overrides/environment controls that make each sentinel inert. Fixture setup also provides no package-script execution path, matching the production adapter's fixed direct Git invocation. Cancellation tests prove the direct child is reaped. Ordering and truncation tests deliberately create more records than the requested public limit.

For P405, the production command policy is fixed: every Git child receives `--no-pager`, `--no-optional-locks`, `GIT_TERMINAL_PROMPT=0`, `GIT_NO_LAZY_FETCH=1`, `GIT_CONFIG_NOSYSTEM=1`, and a product-owned null `GIT_CONFIG_GLOBAL`; the narrow child environment does not inherit `HOME` or other Git-specific variables. Repository discovery additionally clears credentials, hooks, and FSMonitor through command-scoped configuration. History also uses literal pathspecs, disables external diff/textconv, signatures, mailmap, and caller-selected follow behavior before explicitly enabling whole-file `--follow`. Blame uses literal pathspecs and fixed `HEAD`, and its preceding configuration inspection fails closed on reachable repository/worktree external diff, textconv, or ignore-revision behavior.

## Deliberately Deferred

P401 does not approve forge APIs, remotes, fetch/pull/push, mutation, arbitrary revisions, arbitrary Git arguments, submodule traversal, stash/reflog inspection, commit creation, repository discovery above the supplied workspace, or symbol correlation. P407 subsequently found no evidence for an earlier Git/Code composition primitive; Stage 5 is the experimental home for `assess_local_change`, with independently publishable primitive products remaining uncoupled.

## Source Baseline

The contract is grounded in Git's official `git-status`, `git-diff`, `git-log`, and `git-blame` documentation. The history implementation relies on documented `--follow`, NUL-delimited pretty/name-status output, `--line-porcelain`, numeric line ranges, whole-file rename attribution, and `blame.ignoreRevsFile` semantics. Implementation tasks must re-check the official documentation for each additional Git subcommand before fixing command-specific parsing or security policy.
