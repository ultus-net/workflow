## Summary

Task 4 of the C1 Azure control-plane deploy plan, **the return leg**: the
hub-side `validateDispatch(taskId)` evidence-ingest read path plus the
dispatch-record registry. Task 4 built only the enqueue seam (PR #503); this
closes the loop. Spec
`docs/superpowers/specs/2026-09-25-azure-container-jobs-remote-sandbox-design.md`
§6:126-130: "Evidence freshness … stays hub-owned; a run that returns without
declared evidence does not advance state."

- **`src/integrations/azure-jobs-record.ts` (new)** — the return leg, in parts:
  - **The dispatch-record registry** (`createDispatchRecordRegistry`) — the
    hub-held DENOMINATOR. When the hub dispatches a job it records what the job
    DECLARED (`declaredEvidence`, `corpusFingerprint`, the evidence blob path,
    the container, the message id). Without a hub-held record a caller could
    self-satisfy its own coverage check; the record is written only by the hub's
    own enqueue wrapper, never supplied by the client. Both the lookup map and
    the two journals (dispatch records, validation outcomes) are bounded (64),
    oldest-first, with a re-record moving the entry to the freshest position.
  - **`validateWorkerEvidence`** — the structural validator for the worker's
    returned evidence blob (the `images/worker/run.mjs` result record), the
    hub-side intake the image's own copy mirrors. The shapes are pinned to agree
    by a cross-suite test.
  - **`createAzureJobsIngest`** — the `validateDispatch(taskId)` closure with
    the fail-closed outcome matrix: `unknown` (never a fabricated pass),
    `missing`, `invalid` (including a blob whose `taskId` disagrees with the
    requested one), `incomplete` (names the uncovered evidence), `stale-corpus`,
    `failed`, `covered`. Every resolved outcome is journaled; a non-404
    transport fault THROWS so the route 5xx's. A malformed taskId raises the
    typed `DispatchRequestError`. REST only, no Azure SDK — the same shared
    IMDS/azure-cli Bearer chain as the enqueue client.
  - **`createRecordingEnqueue`** — wraps the enqueue closure so a SUCCESSFUL
    dispatch is recorded; a failed enqueue records nothing and a malformed
    message keeps its `AzureJobMessageError` (the 400 classification).
- **Hub route `POST /dispatch/azure-job/validate`** (`hub-http.ts` +
  `workflow-hub.ts` + `cli/hub.ts`) — operator-token class; capability withheld
  → 404; a missing taskId → 400; a resolved outcome → 200 with the structured
  validation; a transport fault → 5xx. The composition root builds one registry
  and wires both legs (the recording enqueue + the ingest closure).
- **Tests** — `test/azure-jobs-record.test.ts` (new, 21 pins: the registry as
  denominator, bounds + reorder, the evidence validator, the full outcome
  matrix, the journaled rule, the Bearer GET, the record's own container, the
  typed client fault, and the recording-enqueue ordering); four validate-route
  pins in `test/azure-jobs-hub-route.test.ts`; and a cross-suite pin in
  `test/worker-image.test.ts` that runs the evidence blob the worker actually
  uploads through the hub's `validateWorkerEvidence`.
- **Docs** — `docs/HUB_PROTOCOL.md` (the route), `docs/CI.md` (53→54 suites),
  plan Appendix C, a new `docs/ledger/control-plane-c1-dispatch-ingest.md`
  fragment, and a supersession note in the dispatch-seam fragment.

**Registry-as-denominator (recorded decision):** the plan left the
`declaredEvidence` source implicit. The hub records the declaration at enqueue
and the ingest checks the returned blob against THAT record; the alternative
(client-supplied expectations) would let the caller self-satisfy the check.
